출석 체크 API는 기록을 DB에 저장한 뒤, 응답을 돌려주고 나서 백그라운드로 이벤트를 발행한다. 이벤트를 받은 컨슈머가 보상을 준다. 발행이 실패하면 재처리 경로가 없었다. 기록만 남고 보상은 안 간다. 사용자 응답은 정상이라 아무도 모른다.

같은 코드베이스의 다른 발행 경로엔 이미 프로세스 안 즉시 재시도가 있었다. 이 경로에만 빠져 있었다. 그걸 채우는 게 과제였다. 최대 4회.

## 정한 것

- **간격.** 2초, 3초, 5초, 10초. 리스트 하나를 상수로 두고 첫 시도 + 재시도 4회. 전부 실패하면 약 20초.
- **응답은 기다리지 않는다.** 발행은 원래 응답 뒤 백그라운드였다. 재시도도 거기서 돈다. API 응답은 0.4초에 돌아온다.
- **로그는 단계별로.** 재시도 끝에 성공하면 info에 시도 횟수. 시도마다 실패는 warn에 `n/5`, 마지막은 `exhausted`. 최종 실패는 error에 추적에 필요한 키(사용자, 날짜, locale).
- **알림.** 모니터링에서 `published after retry`와 `finally failed`를 검색어로 걸어둔다.

## 재시도 전에 확인한 것

재시도는 **같은 이벤트가 두 번 갈 수 있다**는 뜻이다. 보내긴 했는데 응답만 못 받은 경우가 있으니까. 그래서 컨슈머가 같은 이벤트를 두 번 받으면 어떻게 되는지부터 봤다. 멱등하지 않은 컨슈머에 재시도를 붙이면 "안 가는 문제"를 "두 번 가는 문제"로 바꾸는 것뿐이다. 이건 재시도 코드 밖의 일이라 별도 과제로 적어뒀다.

덤으로 기존 버그 하나. 발행이 전부 실패해도 상위 서비스가 "published" info 로그를 찍고 있었다. 운영 로그만 보면 성공으로 읽힌다. 발행 함수가 성공 여부를 반환하게 바꾸고, 성공일 때만 그 로그를 찍는다.

## 가짜 서버로 검증했다

지정한 횟수만큼 500을 주고 그다음부터 200을 주는 Python 서버를 하나 띄웠다.

- 2회 실패 후 성공: 간격이 2.0초, 3.0초로 정확했고 3번째 시도에서 성공.
- 전부 실패: 2/3/5/10초로 진행된 뒤 최종 error. API 응답은 그동안 이미 돌아가 있었다.

겪은 문제 둘. 로컬이 JVM 17로 떠서 실패했다. 21로 올렸다. 그리고 설정 저장소의 값이 커맨드라인 URL 오버라이드보다 우선이었다. 첫 호출이 가짜 서버가 아니라 **개발환경의 진짜 브로커**로 나갔다. 개발환경 DB에 테스트 사용자의 행이 생겼다. 지우고 0건인 걸 확인했다. 설정 우선순위는 테스트 전에 확인할 일이다.

최종 변경은 Kotlin 파일 두 개, +30/−4. DB·설정·컨슈머 변경 없음.

## 이걸로 안 막히는 것

브로커 장애가 20초를 넘기거나 API 파드가 그 사이 재시작되면 여전히 유실된다. 프로세스 안 재시도는 **짧은 흔들림**용이다. 긴 장애까지 막으려면 기록 테이블에 발행 상태 컬럼을 두고 배치가 미발행 건을 다시 보내야 한다. DDL이 필요해서 별도 결정으로 남겼다.

재시도를 넣고 나면 "이제 안 잃는다"고 말하고 싶어진다. 정확히는 "20초 안에 돌아오면 안 잃는다"다. 그 범위를 적어두지 않으면 다음 사람이 재시도를 큐로 착각한다.
