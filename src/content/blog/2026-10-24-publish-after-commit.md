광고를 보면 코인을 주는 리워드 기능이 오래된 Java 서버에 남아 있었다. 그 서버를 없애려고 두 단계로 옮겼다. 큐를 소비해서 지급하는 쪽은 Airflow DAG으로, 광고사 postback을 받는 API는 메인 API 서버로.

## 1단계: 지급 배치

기존 DAG은 3분마다 레거시 서버의 배치 엔드포인트를 호출했고, 그 서버가 SQS FIFO를 꺼내 지급했다. 이 소비 로직을 Python으로 직접 옮겼다. 중복 지급 방어선은 레거시와 똑같이 맞췄다. 성공한 메시지만 삭제, DB 상태 가드, 재시도 0, 동시 실행 1. 설계 원칙은 하나였다. **깨지면 중복 지급이 아니라 지급 중단 쪽으로 깨진다.**

레거시는 실패해도 200을 돌려줬다. 새 DAG은 run 안에 실패가 1건이라도 있으면 태스크를 실패로 표시한다. 조용히 넘어가는 것보다 빨간 불이 낫다.

롤백 전략은 "기존 DAG은 손대지 않고 새 DAG ID를 추가, UI에서 pause/unpause로 전환"으로 정했다. 그런데 배포하자마자 새 DAG이 켜진 채 올라왔다. 기본값이 꺼짐이라고 믿었는데, 저장소의 도커 설정만 보고 운영 인스턴스 설정은 확인 안 한 거다. 둘이 동시에 돌았으니 중복 지급을 의심할 수밖에 없었다. 구매 내역과 이벤트 테이블의 지급 시각을 1:1로 대조했다. 중복은 없었다. 방어선이 두 겹이라 둘이 같이 돌아도 한 번만 지급됐다. 설계가 맞았다는 걸 사고로 확인한 셈이다.

## 2단계: 수신 API

광고사 세 계열, 엔드포인트 아홉 개를 메인 서버로 옮겼다. 원칙은 "기존 동작 완전 그대로". 쓰이는지 불확실한 API도 똑같이 옮기고, 레거시의 숫자 파싱 버그도 고쳤다가 원복했다. 이관과 개선을 한 배포에 섞으면 문제가 생겼을 때 어느 쪽인지 모른다.

검증은 두 서버를 로컬에 띄우고 같은 요청을 보내 응답 코드·본문·DB 행·발행된 이벤트·DAG 처리 결과까지 대조하는 방식. Redis 캐시 키도 직접 비교했다. 그래도 배포 뒤에 네 개가 나왔다.

**캐시를 못 읽었다.** 레거시는 Redis에 JDK 직렬화로 저장했고, 새 서버는 JSON으로 바꿨다. getter/setter 이름이 안 맞아 역직렬화가 실패했다. 응답은 정상이었다. 다만 요청마다 외부 API를 다시 부르고 있었다. 결과가 맞으면 아무도 모른다.

**시각이 UTC로 저장됐다.** 리전 차이가 아니라 JVM 기본 타임존 차이였다. 매퍼와 타입 핸들러를 고치는 안이 나왔지만, 시각을 만드는 네 곳만 고치는 최소 수정으로 갔다.

## 0.5%가 영원히 못 받았다

세 번째가 이 글의 제목이다. 이틀 치를 보니 약 0.5%가 미지급이었다. 재시도도 안 됐다. 메시지가 큐에서 사라져 있었다.

순서가 문제였다. postback을 받으면 DB 트랜잭션 안에서 행을 쓰고, **같은 트랜잭션 안에서** SQS에 지급 메시지를 보냈다. DAG이 그 메시지를 커밋 전에 읽으면 행이 안 보인다. DAG은 "이미 지급됐거나 대상 아님"으로 판단하고 메시지를 삭제한다. 커밋은 그 직후에 된다. 행은 있고 메시지는 없다. 영구 미지급.

레거시에서 왜 안 터졌냐면, 거의 안 터졌을 뿐이다. 새 서버 파드와 DB 리전이 달라 커밋까지의 창이 길어졌고, 그 창에 DAG의 3분 주기가 걸리기 시작한 거다. 같은 코드가 지연 하나로 버그가 된다.

발신을 **커밋 이후**로 옮겼다. 처음엔 트랜잭션 동기화에 직접 등록했다가 저장소 컨벤션인 `@TransactionalEventListener`로 바꿨다. `@Async`는 뺐다. 응답 코드를 그대로 유지해야 했으니까. "커밋은 됐는데 발신이 실패한" 반대 케이스는 레거시와 같은 동작이라 손대지 않았다.

## 네 번째: 알람이 시끄러웠다

정상 차단 경로가 error 레벨로 찍혀 웹훅이 울렸다. 원인 중 하나는 해외 앱이 SDK 연결이 끝나기 전에 사용자 ID를 설정해서, ID 자리에 UUID가 들어온 것. 원칙을 정했다. **시스템 오류만 error, 정상 차단은 warn, 매번 타는 정상 경로 로그는 삭제.** 공통 예외 핸들러 경로를 처음에 빠뜨려서 두 번에 나눠 고쳤다.

## 덤: 새 태스크가 계속 죽었다

운영 중 ECS 새 태스크가 기동 실패를 반복했다. 배포 도구가 직전 태스크 정의를 통째로 복사하는데, 옛 Command에 남아 있던 APM 에이전트 jar 경로가 따라왔다. 그 jar는 두 달 전 Dockerfile에서 빠진 상태. k8s 쪽은 Command 재정의가 없어서 멀쩡했다. 첫 가설이 이거였는데 중간에 접었다가 실제 에러 로그로 돌아왔다. 가설은 버리지 말고 로그로 기각해야 한다.

## 정리

- 트랜잭션 안에서 큐에 보내면 "커밋 전에 소비"가 가능하다. 레거시에서 안 터진 건 운이었다.
- 이관은 동작을 그대로 옮기고, 개선은 다음 배포에.
- 결과가 맞는데 비용이 틀린 버그(캐시 미스)는 로그 말고 호출 수를 봐야 보인다.
