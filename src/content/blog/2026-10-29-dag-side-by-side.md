3분마다 레거시 서버의 엔드포인트를 curl로 때리던 DAG이 있었다. 그 서버가 큐를 꺼내 처리했다. 서버를 없애려고 소비 로직을 DAG 안으로 옮겼다. 코드 자체는 어렵지 않았다. 어려운 건 **어떻게 바꿔치기하고 어떻게 되돌릴 것인가**였다.

## 롤백 전략이 세 번 바뀌었다

**① 같은 DAG ID 덮어쓰기.** 제일 단순하다. 그런데 롤백하려면 git revert와 재배포가 필요하다. 그동안 3분마다 새 코드가 계속 돈다. 큐 소비 로직에서 그 몇 분은 길다.

**② 기존 코드를 백업 DAG으로.** 기존 코드를 새 DAG ID에 paused 고정으로 복사해 두고, 원래 ID를 새 코드로 덮는다. 롤백은 UI에서 백업을 켜면 된다. 되긴 되는데 파일이 두 벌이고, 원래 ID가 "새 코드"가 된 상태라 나중에 헷갈린다.

**③ 기존 파일은 손대지 않고 새 DAG ID로 추가.** 전환은 기존 pause + 새것 unpause. 롤백은 그 반대. 코드 배포 없이 UI에서 끝난다. 브랜치도 분기점으로 되돌려 "신규 파일 추가" 한 커밋으로 정리했다. 기존 파일은 이력상 아예 안 건드린 상태.

③으로 갔다. 전환과 롤백이 대칭이고, 둘 다 배포가 필요 없다는 게 결정적이었다.

## 동시에 켜지면 안 된다

③의 유일한 위험은 둘이 동시에 켜지는 것. 두 소비자가 같은 FIFO 큐를 읽는다. 그래서 절차를 정했다.

1. 새 DAG이 **paused 상태로** 생성됐는지 확인.
2. 기존 DAG pause. 실행 중인 run이 끝날 때까지 대기.
3. 3분 안에 새 DAG unpause.

1번이 핵심인데 여기에 함정이 있었다.

## pause 기본값은 두 겹이다

DAG에 `is_paused_upon_creation`을 안 주면 인스턴스 설정 `dags_are_paused_at_creation`을 따른다. Airflow 기본값은 True다. 저장소의 도커 설정 어디에서도 이 값을 바꾸지 않았다. 그래서 "꺼진 채로 생성된다"고 믿었다.

운영 인스턴스 설정은 저장소와 달랐다. 새 DAG이 켜진 채 올라왔다. 저장소 설정을 본 게 아니라 **운영 인스턴스의 실제 설정**을 봤어야 했다. 지금은 모든 신규 DAG에 `is_paused_upon_creation=True`를 명시한다. 기본값에 기대지 않는다.

하나 더. 이 인자는 **메타DB에 처음 등록될 때만** 적용된다. 기존 DAG ID를 덮어쓰면 기존 unpaused 상태를 그대로 이어받는다. ①번 전략이었다면 이 인자가 아무 의미가 없었을 거다.

## 저장소에서 발견한 관례들

- 31개 DAG이 `exclude:<환경>` 태그를 달고 있는데, 이 태그를 읽는 코드가 저장소 어디에도 없다. 순수 문서용 관례였다. 실제로 환경별 실행을 막는 건 `is_paused_upon_creation = (env != prod)` 패턴과 코드 안의 env 가드.
- 코드에 `aws_default` Connection의 권한을 확인하라는 TODO가 있어서 한참 찾았다. 인스턴스에 그런 Connection은 없었다. 훅 생성자의 파이썬 기본 인자값이었고, README 예시를 그대로 따른 흔적이었다. 실제로 있는 Connection을 UI에서 먼저 세고 시작했어야 했다.
- 훅은 Extra에 리전이 없으면 us-east-1을 기본으로 쓴다. 코드에 리전 상수를 뒀다.

## 원본과 일부러 다르게 간 곳

레거시 서버는 처리에 실패해도 로그만 남기고 200을 돌려줬다. 새 DAG은 run 안에 실패가 1건이라도 있으면 마지막에 예외를 올려 태스크를 실패로 만들고 알림을 울린다. 운영 파라미터는 3분 주기, 동시 실행 1, 재시도 0. 중복 처리 방어선은 "성공한 메시지만 삭제"와 DB 상태 가드 두 겹.

설정이 빠졌을 때 어떻게 실패하는지도 표로 정리했다. 권한 없음은 태스크 실패로 드러나는데, 토큰이나 호스트가 틀린 경우는 **성공으로 표시되는** 함정이 있었다. 조용히 성공하는 실패가 제일 늦게 발견된다.

## 정리

- 전환과 롤백은 대칭이어야 하고 둘 다 배포 없이 돼야 한다. 그러려면 기존 것을 덮지 말고 옆에 둔다.
- 기본값은 저장소가 아니라 운영 인스턴스에서 확인한다. 그리고 가능하면 명시한다.
- "처음 등록될 때만" 적용되는 설정은 덮어쓰기 전략과 상극이다.
